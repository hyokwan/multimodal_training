## 주요 동작 — getCollateFn / collateFn

### system 메시지 + 이미지 호환성 (모델 독립적)

`buildMessages()`는 항상 `system` / `user` / `assistant` 3턴 구조를 만들었는데, Llama 3.2 Vision
(Mllama) 같은 일부 모델의 채팅 템플릿은 **이미지가 포함된 대화에서 system 역할을 금지**합니다
(`jinja2.exceptions.TemplateError: Prompting with images is incompatible with system messages.`).
Gemma3는 이 조합을 허용하므로 문제없이 동작했지만, 다른 모델로 `BASE_MODEL`을 바꾸면 이 에러로
학습이 바로 실패했습니다.

`getCollateFn()`이 시작될 때 `systemMsgSupportsImage(processor)`로 더미 이미지+system 메시지를
실제 채팅 템플릿에 1회 프로브해서 지원 여부를 판별하고, 그 결과(`mergeSystemToUser`)를
`buildMessages()`에 전달합니다.

| `mergeSystemToUser` | 이미지 있는 샘플 | 이미지 없는 샘플 |
|---|---|---|
| `False` (Gemma3 등 system+이미지 지원) | `system` / `user`(이미지+텍스트) / `assistant` — 기존과 동일 | 동일 |
| `True` (Llama 3.2 Vision 등 미지원) | `user`(이미지 + `system텍스트\n\nuser텍스트`) / `assistant` — system 턴 없음 | `system` / `user` / `assistant` — 이미지가 없으므로 제약 없음, 기존과 동일 |

`collateFn` 내부에서 user 턴을 찾을 때도 `messages[1]`처럼 인덱스로 고정하지 않고
`role == "user"`로 탐색합니다 (병합 시 메시지 개수·순서가 바뀌므로 인덱스 고정은 버그였음).

### 배치 처리 3-way 분기

`collateFn` 은 배치 내 샘플 구성에 따라 3가지 경로로 분기합니다.

| 경우 | `nestedImages` 구조 | 처리 방식 |
|------|-------------------|----------|
| 전부 text-only | `[None, None, ...]` | `processor(text=...)` — images 없이 호출 |
| 전부 image-text | `[[img1], [img2], ...]` | `processor(text=..., images=nestedImages)` 단일 호출 |
| 혼합 | `[[img1], None, [img3], ...]` | 분리 처리 후 `_mergeMixedBatch` 로 병합 |

### 핵심: `[[img]]` 중첩 리스트 구조

`make_nested_list_of_images` 의 동작:
- `[img1, img2, ..., imgN]` (flat) → 이미지 N개짜리 **배치 1건** → `len = 1 ≠ N` → 에러
- `[[img1], [img2], ..., [imgN]]` (중첩) → 1이미지씩 **N개 배치** → `len = N == N` → 정상

### _mergeMixedBatch 동작

혼합 배치 처리 시 호출되는 내부 함수:
1. `imgBatch = processor(text=imgTexts, images=imgImages)` — 이미지 샘플 서브배치
2. `txtBatch = processor(text=txtTexts)` — 텍스트 샘플 서브배치
3. 두 배치의 `input_ids`, `attention_mask`, `token_type_ids` 를 maxSeqLen 으로 패딩 후 원본 인덱스 순서로 합산
4. `cross_attention_mask` (Llama 3.2 Vision/Mllama 계열만 존재) — 텍스트 축(dim=1)만 maxSeqLen 으로
   패딩 후 원본 인덱스 위치에 배치, 텍스트 전용 샘플 자리는 0(이미지에 cross-attention 안 함)으로 채움.
   이 키가 없는 모델(Gemma3 등)은 그냥 건너뛰어 기존 동작과 동일.
5. 그 외 이미지 서브배치에만 있는 키(`pixel_values`, `aspect_ratio_ids`, `aspect_ratio_mask` 등)는
   텍스트 전용 샘플에 대응 항목이 없으므로 그대로 전달 (이미지 토큰 등장 순서로 모델이 내부 매핑)

> 과거에는 `pixel_values`만 하드코딩으로 통과시켜서, Llama 3.2 Vision처럼 `aspect_ratio_ids` 등
> 추가 텐서를 요구하는 모델은 혼합 배치(이미지+텍스트 섞인 배치)에서
> `aspect_ratio_ids must be provided if pixel_values is provided` 에러로 실패했음.
> 이제 이미지 서브배치의 키를 전부 훑어 자동으로 통과시키므로 모델별 하드코딩 없이 대응됨.

### 이미지 토큰 loss 마스킹 (모델 독립적)

이미지 토큰은 loss 계산에서 제외해야 하므로, `model.config` 에서 이미지 토큰 ID를 동적으로 조회합니다.
HF 모델 계열마다 속성명이 달라 두 가지를 순서대로 확인합니다.

```python
imageTokenId = getattr(model.config, "image_token_id", None)
if imageTokenId is None:
    imageTokenId = getattr(model.config, "image_token_index", None)
if imageTokenId is not None:
    labels[labels == imageTokenId] = -100
```

| 모델 | 사용 속성 | 값 |
|------|----------|-----|
| Gemma3 (`google/gemma-3-4b-it`) | `image_token_id` (`image_token_index` 와 동일값) | 262144 |
| Llama 3.2 Vision (`mllama`) | `image_token_index` | 128256 |
| Llama4 | `image_token_index` | 200092 |

과거에는 Gemma3 값(262144)을 코드에 직접 하드코딩해두어, `BASE_MODEL` 을 다른 모델 계열로
바꾸면 이미지 토큰이 loss에서 제외되지 않는 문제가 있었음 (에러 없이 조용히 학습 품질 저하).
동적 조회로 변경해 `BASE_MODEL` 교체 시에도 정상 동작하도록 수정.
